# Android verification and data compatibility

Use JDK 17 and Android SDK 34. Run from `android/`:

```sh
./gradlew testDebugUnitTest lintDebug assembleDebug --console=plain
```

Windows: use `gradlew.bat`. Keep `GRADLE_USER_HOME`, `ANDROID_USER_HOME`, and temporary directories on the configured development disk. CI runs the same checks and retains reports. Tests use fake data and intercepted HTTP calls; they do not contact lottery or AI services and do not use real credentials.

## Upgrade behavior

- Prediction schema V3 adds the nullable `archive_entry_id` link and separate `collected_batches`, `ai_request_archive`, `ai_archive_payload`, and `recommendation_entries` tables. Migration preserves V2 rows, IDs, flags, text and the AUTOINCREMENT sequence; failed DDL rolls back. Older builds that only understand V2 cannot open a migrated V3 database.
- Prediction schema version 2 adds explicit entry kind, KL8 play, blue-ball source and full timestamps. Existing records keep their IDs, numbers, strategy, note and original time text. Their kind remains `LEGACY_UNCONFIRMED`; no play or missing year is invented. They display hits rather than a definitive single-ticket prize. Unknown lottery types are quarantined rather than reassigned to SSQ. No uniqueness constraint prevents saving multiple plans for one issue.
- New predictions require reviewing the target issue and complete numbers before saving. Red-only heart selections are reference pools. Compound and reference pools are not evaluated as single tickets. Batch confirmation is one database transaction.
- Local next-issue suggestions preserve width but are provisional. Old data and year-end boundaries have no automatic issue suggestion; users confirm the official issue before saving. There is no hard-coded annual draw count or holiday calendar.
- Legacy plaintext AI credentials are encrypted using an Android Keystore AES-GCM key before the old preference is removed. Credentials are scoped by provider and endpoint. A provider/endpoint change clears the editor's key. Restored or invalid ciphertext is removed and requires reconfiguration. Both backup formats exclude credential preferences and diagnostic logs.

## Window-frequency strategies

- Tools > 选号推演 adds a separate window-frequency card for SSQ/DLT. It uses the local history, numeric issue ordering, and 1–1000 requested periods (30/50/100 shortcuts). The actual sample count and issue range are displayed. Invalid draws and duplicate issues are excluded and counted; conflicting results for one issue fail explicitly. Missing/omission groups remain independent.
- Kotlin-only generation supports balanced, frequency-weighted hot/cold, balanced zones, and at least one consecutive red pair. These are descriptive heuristics, not a fitted prediction model. Presets and custom red/blue counts are validated; each batch contains distinct pools. Different compound pools can overlap in their constituent single tickets.
- Combination counts use both zones and are calculated without expanding tickets. Compound entries still show hits rather than single-ticket prizes. Existing confirmation and prediction-schema V2 storage are reused. Strategy text retains engine version, strategy, requested/actual window, issue range, pool sizes, seed, and group index; no schema migration or new dependency is introduced.
- Statistics and generation run on the compute dispatcher with cancellation checks. Data/parameter changes discard old output, and leaving the screen cancels work. Inputs survive configuration recreation; generated output is transient. Only explicit user actions generate or stage predictions. Existing KL8 tools are unchanged.
- JVM regressions cover window ordering/deduplication, zero frequencies, invalid/conflicting data, boundary histogram bins, sample statistics, all strategies and formats, deterministic seed replay, batch uniqueness, combination counts, and cancellation. Device acceptance: switch lottery/window during work; rotate with custom settings; inspect blue balls in compound results; stage a batch, cancel/reopen confirmation, and save/reload its metadata. There is no Excel import or compound payout calculation in this increment.

## AI frequency integration

- The AI workbench has independent, saved history-frequency settings (enabled by default, 50 periods, balanced preference). SSQ/DLT support 1–1000 periods and all five strategies. KL8 hides these controls and never invokes the SSQ/DLT frequency engine.
- Each request retains one history and parameter snapshot. The workbench uses the latest valid local draw, independent of the draw currently being browsed. Omission facts and frequency statistics are built from this same cutoff. A specified target must follow the cutoff; a blank provisional target remains unconfirmed. Historical builder tests use explicit cutoffs to exclude later draws. Only one omission state is retained during AI preparation rather than an omission map for every historical draw.
- The prompt distinguishes historical draw counts, omissions, user choices, and other users' selections. Compact complete frequency tables (including zeros) are supplemented by rankings and empirical shape distributions. Hot/cold/balanced are preferences; balanced red zones and at least one consecutive red pair are hard rules. These heuristics do not establish improved winning odds.
- Only legal single tickets pass the new parser. Duplicate or out-of-range values, extra tokens and malformed lines invalidate the entire group. Structured recommendation output is never rescued by mining prose; unlabelled numeric lines are ignored even when no recommendation tags exist (guardrails-v2). Groups are deduplicated, capped to the requested count, checked against selected hard rules and fusion overlap constraints, and returned with rejection reasons. Empty/partial results remain visible; no additional model request is automatically issued to fill missing tickets.
- Results display requested/recognized/retained counts, exclusions, cutoff, requested model and window. Existing confirmation/storage are reused; AIv2 strategy text captures original provider/model and frequencyv1 strategy/window/range. There is no LLM seed or claim of model replayability. Editing window settings cancels and invalidates old results, including late responses.
- Offline checks cover facts/cutoffs/omission consistency, prompt fact separation, strict SSQ/DLT/KL8 parsing, strategy and fusion constraints, partial/empty output, request snapshots, late-response invalidation, saved settings and provenance. No real model API was called. Device acceptance still includes chip/window editing, rotation, KL8 switching, partial-result rendering and the prediction confirmation flow.

## Memory archive: Phase 1

- Both Tools and Prediction Compare expose the same archive card and AI frequency settings. The card previews recent request states, original/rejected candidates, user-confirmed revisions and saved collection batches. Detail reads are lazy, on IO, and bounded (10 recent runs, 5 batches, up to 200 candidate previews / 100 collected-group previews).
- Collection snapshots are written only on an explicit archive action, an AI request, or prediction confirmation. Normal typing/debounce creates no history. Exact snapshots deduplicate by type/target/origin/content hash; raw collector input is limited to 20,000 characters. Undeclared collected groups remain reference pools; no KL8 play is invented.
- Before invoking the model client, a transaction commits a PENDING request, optional collection link and a credential-free prompt/fact snapshot. The actual client receives the same prepared prompt envelope. An archive failure prevents dispatch. Whitelisted DTOs contain no AiConfig, API key or Authorization header. Failure diagnostics store categories (including HTTP status/timeout), not raw exception bodies.
- Successful responses archive recognized original rows, rejected rows/reasons and accepted indices. The accepted track is a view of the original rows, not duplicated samples. Every generated accepted group is archived even if the user never saves it. User confirmation creates a new USER_FINAL entry linked to the original; prediction insertion and that entry share one transaction. Editing/confirmation times are separate. Deleting an item from the prediction list does not delete its independent audit archive.
- Terminal states are COMPLETED / PARTIAL / FAILED / CANCELLED / INTERRUPTED. Completion and terminal updates are idempotent. At startup, PENDING rows from another process session become INTERRUPTED (remote execution unknown); nothing is resent. A response that arrives after UI invalidation is archived before the existing generation guard discards it from the screen. `finish_reason` is recorded when supplied, including length-limited partial results.
- Timing is conservative: the local presence of a draw marks a recording as POST_DRAW; otherwise it is INSUFFICIENT_TIMING_EVIDENCE. Phase 1 has no trusted external draw-time authority and never invents CONFIRMED_PRE_DRAW status. Source/origin labels do not grant eligibility. Each original and user revision retains its own qualification.
- Large optional prompt/response payloads are capped at 65,536 characters with truncation flags. Structured facts, candidates, relationships and timings are retained. Startup cleanup only removes optional payloads of old failed/cancelled/interrupted runs beyond 100; successful/unsettled plans remain protected. Phase 2 will define settled-plan cleanup. This paragraph describes the original Phase 1 baseline; Phase 2/3 behavior is described below.
- JVM SQLite/coroutine tests cover V1/V2 migration, exact V2 field/ID/sequence preservation, rollback, collection deduplication and explicit-action capture, credential exclusion, pre-send commit ordering/failure, original/rejected/accepted relationships, idempotency, user edits without overwriting originals, atomic prediction/archive rollback, cancellation, process recovery and payload retention. No real model endpoint is called.

## Archive input and payload compatibility

- Collection input uses one 20,000-character policy across the editor, ViewModel, coordinator and archive store. The editor displays the live count and validation error. An oversized editable draft is not parsed, its old frequency result is cleared, and new recommendations/collection commits are blocked with a specific error before dispatch. The last valid draft remains the SavedStateHandle restoration value; oversized text is not added to the saved-state bundle. Previously archived AI plans can still be confirmed using their original collection link rather than the oversized current editor contents.
- Archive dialog visibility, target, source and origin reset when lottery type changes; target also follows the suggested-issue input key. Both AI workbench entry points receive the same collection validation state. Device acceptance must still check switching between lotteries with identical/blank suggested issues, dismiss/reopen and Activity recreation.
- The coordinator validates endpoint syntax/host/scheme before creating a run or invoking the model client. Invalid URLs return a configuration-specific error without echoing the URL or falling back to an empty host. The existing HTTP(S) scheme policy is unchanged by this increment. Storage failures still prevent dispatch.
- Structured facts, collected groups and prompt envelopes now carry `payload_schema_version=2`. `ArchivePayloadCodec` explicitly writes named JSON properties, including all nested analysis/window fields; it does not reflect over business DTO or kotlin.Pair field names. Primitive candidate-number arrays and rejection maps keep their existing stable representation. Payload and SQLite schema versions are independent; the database is now V4.
- Readers accept existing unversioned groups (`first`/`second`), facts and prompts, and normalize facts to the explicit v2 JSON protocol. Unknown versions and malformed number arrays fail rather than being guessed. Legacy collection hashes are reconstructed with explicit field names and the original escaping rules, so saving an existing batch reuses its original ID/hash/payload without rewriting or duplicating it.
- Added offline tests cover legacy/current payload reads, complete nested-field preservation, hashes with HTML/non-ASCII characters, stable dedup against old SQLite rows, unknown versions, integer validation, malformed URL preflight without archive/network activity, exact input-limit boundaries, rejection of oversized drafts and confirmation of an already archived AI plan. No real API or device tests were run.

## Memory settlement and controlled recommendation: Phases 2 and 3

- SQLite V4 adds versioned `archive_evaluations`, active `archive_draw_heads`, source invalidation epochs and policy state. V3 archive fields, IDs, payloads, relationships and legacy prediction flags remain intact. ALTER operations and version updates share the existing migration transaction. Old records receive no invented prospective protocol or seed. A frozen V3 SQL fixture tests actual old-table upgrades, repeat upgrades and rollback.
- Startup, completed draw synchronization, archive refresh and a new memory-enabled AI request settle matching local draws. This is foreground/startup reconciliation, not a scheduled background download. No matching draw leaves a plan pending. Invalid draw numbers never become active results. Source epochs avoid repeating Monte Carlo work when neither the archive nor draw changed; epochs invalidate caches and are not performance totals.
- Settlement is serialized per lottery, computes outside the write transaction, rechecks source epochs, then upserts stable `(subject_id, draw_revision, rule_version)` rows and an active head atomically. Official corrections preserve old revisions. Queries join the active revision, so repeated synchronization never adds duplicate wins. Cancellation/failure cannot publish a partial issue. Structured numbers, facts, candidate IDs and timing evidence remain available for recomputation.
- The comparison card separates collected reference pools, legal AI originals, accepted AI entries, user confirmations and local candidates. It buckets by lottery, kind, play, red/blue counts and qualification. First average within each issue/bucket, then average the issue means; 100 plans for one draw are still one draw. Formal, unknown, post-draw and review records are separate. Formal/observation issue counts can overlap if one issue contains both kinds of record. Unparseable/illegal rows remain in the archive and compliance counts, but cannot have a legal-ticket outcome.
- Fixed seeded controls are frozen independently of the draw. Unconstrained same-shape controls use 64 samples. Matched hard-rule/fusion controls attempt up to 4,096 draws to retain 64 legal samples; below 32 samples, the corresponding grouped comparison is unavailable. No unconstrained distribution is substituted for a constrained control. AI-selected entries additionally compare against a preshuffled same-candidate-pool subset with exactly the retained group count. These are finite Monte Carlo diagnostics, not significance or ROI claims. Compound/reference pools show hit counts only.
- The workbench defaults to two-stage generation: generate up to 16 unique legal single-ticket candidates locally (12/16/20 controls), then ask AI to select IDs. SSQ, DLT and KL8's ten play sizes use shared hard validation. Local code computes sum, odd/even, zones, adjacent pairs, heart overlap and collected-pool overlaps. Frequency facts are used where supported; KL8 uses omission preferences without invoking the SSQ/DLT frequency engine. HOT/COLD/BALANCED/SEGMENT/CONSECUTIVE are heuristic candidate families, not learned lottery probabilities. Seeds, family, generator/evaluation versions, full candidates and independent control order are archived before HTTP dispatch.
- Selection responses use `candidate_ids` JSON. Unknown IDs, repeats, non-string values, hard-rule violations and excess IDs are rejected individually; truncated/unparseable JSON retains no guessed groups. There is no automatic retry or invented replacement. Accepted rows refer to their original local candidate; user confirmations remain a separate child revision. The UI displays requested/parsed/retained counts and exclusions. Disabling two-stage generation uses the strict tagged legacy format.
- Memory summaries use only results through the frozen analysis cutoff. Policy keys isolate play, hard-rule mode, frequency/omission basis, requested frequency window and generator version. Adaptive family scores use one normalized excess-hit score per issue/family against matching constrained controls. At least 30 formally qualified issues, a conservative bounded-score confidence penalty, a 10% exploration floor and a maximum five-percentage-point change per new formal issue apply. Same-issue refresh cannot keep increasing weights; corrected evidence freezes current weights until a new formal issue. A stored policy from after the requested cutoff is ignored and never overwrites that future state. History, count and enable switches survive Activity recreation.
- **Production timing gate:** this app still has no trusted external draw-time authority. Local draw presence implies POST_DRAW; absence implies INSUFFICIENT_TIMING_EVIDENCE. Neither a manually selected origin nor a local clock certifies pre-draw status. Thus existing/new ordinary records are visible observations and the adaptive policy remains uniform until a real certification integration supplies valid evidence. Synthetic certification is used only in offline tests. Candidate generation, AI selection, settlement and observed comparisons work independently of that gate. Historical hit rates never imply improved next-draw odds.
- Collector parsing now reports ambiguous odd compact-number lengths, repeated/out-of-range values, negative/decimal/range input and multiple separators; KL8 rejects a blue-ball separator. A draft with any rejected row blocks recommendation/new archive capture until corrected rather than silently using only its valid subset. Valid two-digit compact forms and one-line-per-group input remain supported. Archived accepted plans can still be confirmed independently of a later invalid draft.
- Optional raw prompt/response payloads of terminal settled runs can roll off beyond the latest 100 eligible runs. Candidate-bearing unsettled or dirty-head runs and PENDING runs are protected. Terminal failures without any candidate rows remain eligible under the prior policy. Facts, numbers, relationships, revisions, timings, seeds and evaluation rows are never pruned. No new library or real service call is required for these features.
- Offline coverage includes all lotteries/play sizes, deterministic legal candidates/features, impossible constraints, ID-only responses, strict collector failures, V3/V4 preservation/rollback, source invalidation, official corrections/idempotency, per-issue averaging, shape/origin qualification, cancellation/write failure, corrupted facts, control reproducibility, future-policy isolation, synthetic formal tuning/refresh/correction bounds, payload protection and ViewModel settings/request snapshots.

## Device acceptance still required

JVM tests verify HTTP cancellation/error handling, paging decisions, snapshot publication, credential scope/AES-GCM, schema SQL migration, prediction semantics, ViewModel failure handling and state restoration. They do not replace Android-device tests of Keystore, backup/restore, Activity/process recreation or rendering/frame timing.

Before public distribution, provide a stable release signing identity and test the SDK migration appropriate to the distribution channel. Google Play submission requires target API 36; this private-install build retains the existing API 34 target. R8 is a separate optimization that requires reflection/serialization regression checks. No release key is generated or committed by this change.
